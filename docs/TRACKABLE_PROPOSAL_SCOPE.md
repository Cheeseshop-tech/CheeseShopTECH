## 3. Architecture options

### 3.1 The fork the brief asked to be surfaced clearly

**Static-file-plus-pixel** vs. **served-dynamic-page-per-recipient** are genuinely different
systems, not two configurations of the same one:

**Option A — Tracking pixel/beacon embedded in a still-static HTML proposal.**
The proposal remains a generated static file (emailed as an attachment or hosted as a plain
HTML page); a 1x1 image or `fetch()` beacon on load reports "opened" to a logging endpoint.
- Keeps the existing generation model intact (whatever renders the proposal — even
  browser-print like `invoice.js` today — doesn't need to change).
- Gets open tracking and rough distinct-session counts.
- **Cannot** get real section/page-level engagement without adding real JS instrumentation to
  every generated proposal (scroll listeners, IntersectionObserver on each block) — doable, but
  the proposal stops being "just a static file" the moment it does this.
- **Cannot** cleanly get a unique link per recipient unless each send already produces a
  distinct file/URL (e.g., a UUID-named HTML file per send) — extra generation-time work.

**Option B — Unique-URL-per-recipient microsite (what Paperflite actually does).**
Each proposal send creates a database record (recipient, proposal content reference, token) and
is served dynamically at `proposals.cheeseshoptech.com/<token>` (or a client subdomain) from a
Netlify Function or small backend, reading engagement events live.
- Matches the actual competitive feature being copied — full page-level analytics, one clean
  link, no attachment-vs-hosted ambiguity.
- Requires: a datastore (see 3.2), a serving function, and a real routing/token scheme —
  meaning this is the first genuine backend service in the org's stack.
- The proposal necessarily becomes "a served page," not "a generated file" — this is the
  architecture fork. It's a bigger lift, but it's the only option that satisfies the brief's own
  must-have row ("unique link per proposal... not a shared static file").

**Recommendation surfaced, not decided:** given the brief's own must-have list requires a
unique link per recipient and open tracking, Option A only gets there with extra plumbing that
converges on most of Option B's requirements anyway (a datastore, a token, a logging endpoint).
Option B is more work up front but is the only one that cleanly satisfies the stated MVP without
a second migration later. This is exactly the kind of call the brief says not to make here — but
naming the convergence is different from picking the architecture, so surfacing it for Rick.

### 3.2 Datastore for event logging

Three real options, evaluated against what's already in the stack:

- **Netlify Blobs** — zero new vendor, same platform already hosting everything. Simple
  key-value; workable for "did X open, when" but awkward for querying/aggregating engagement
  across many proposals for a dashboard (no real query language).
- **Supabase (Postgres)** — new vendor, but gives real relational queries for the dashboard
  (§ engagement rows: sent/opened/sections-viewed/last-activity need joins and aggregation that
  a KV store makes painful). `CANONICAL_SCHEMA.md`'s own v1.2 notes in `Monti-Trentini-shop`
  independently arrive at "the day you outgrow single-JSON-file reads, swap to Netlify Blobs /
  Supabase" for the *unrelated* movement-report feature — i.e., this precise fork was already
  anticipated by earlier work, for a different reason. Worth reusing the same choice for
  consistency rather than picking two different datastores for two different platform features.
- **Fauna** — named in the brief; no longer a clearly-supported managed offering as of this
  writing and not used anywhere else in the stack. Would not recommend introducing a third
  datastore vendor when Blobs and Supabase already cover the range.

**Note:** whichever is chosen, it's the org's first real "shared state that isn't a JSON file
in git" — a genuine platform decision, not a proposal-builder-only one. Reinforces open question
3 (§5) about whether this belongs in UDCS/platform scope rather than being proposal-specific.

### 3.3 Riding on the existing pipeline vs. requiring a new one

There is no existing Puppeteer/pptxgenjs pipeline to ride on (§1.2). The real existing
pattern is `invoice.js`'s browser-print flow, which is generation-only and produces a static
PDF with no ongoing connection back to a server. Tracking cannot ride on that pattern at all —
by the time a PDF is "printed" client-side, there's no code left running to report anything.
So this isn't "does tracking bolt onto the current pipeline" (it doesn't and can't) — it's "the
Proposal Builder's own generation approach needs to be chosen with tracking as a first-class
requirement," which folds this decision into the Builder's still-open questions (brief §5,
items 1–2) rather than something layered on after.

## 4. Effort estimate

Sizing is necessarily rough given two of the brief's own open questions (Design Theme Engine
scope, "product placement zone" meaning) are unresolved inputs. Two scenarios:

**Scenario 1 — Tracking layered onto an already-shipped Proposal Builder** (assumes the
Builder's own open questions get resolved and it ships first, independent of this work):
- Token/unique-link generation + routing: **Small–Medium**
- Datastore setup (Blobs or Supabase) + event-logging endpoint: **Small**
- Open tracking (pixel/beacon) + distinct-session counting: **Small**
- Section/page-level engagement instrumentation: **Medium** (meaningfully more JS + event
  volume than open tracking; this is usually where "should-have" scope quietly becomes "v2")
- Rep notification via Make: **Small** (existing connected infra)
- Engagement dashboard (even a minimal one): **Medium–Large** — this is really "build the
  first panel of the platform's still-unbuilt Phase 2 dashboard," so its size is coupled to
  platform work outside this feature's own scope.
- **Total, must-have + should-have:** Medium overall, with the dashboard row as the long pole
  and the biggest source of estimate risk.

**Scenario 2 — Tracking designed in from the start, Builder built alongside it** (more
realistic given §1.3 — there's no Builder to layer onto yet):
- All of Scenario 1's line items, plus the Proposal Builder's own generation engine
  (template rendering, theme handling, PDF/HTML output) which the original scope doc parked
  and never sized.
- **Total: Large** — this is effectively "build a new product," not "add a feature."

**The estimate that matters for a greenlight decision:** the delta *tracking specifically* adds
on top of an already-committed-to Builder build is Small–Medium (Scenario 1's math). The
delta if this is being used to justify building the Builder itself is much larger and is really
a Builder-scoping question, not a tracking-scoping one — reinforcing brief §6's sequencing note.

## 5. Dependency list

What has to be true/decided before a build could start, in rough order:

1. **Proposal Builder's own parked questions resolved** (brief §5.1–5.2): is the five-theme
   Design Theme Engine a live client feature or an agency demo; what "product placement zone"
   means. Blocks knowing what's actually inside a proposal to instrument.
2. **Generation model decided**: does the Builder render server-side (enabling a served
   dynamic page, Option B) or continue the org's existing static/client-side pattern (forcing
   Option A's workarounds)? This is now also a Builder decision, not just a tracking one (§3.3).
3. **Datastore choice made** for event logging (§3.2) — ideally decided once, at the platform
   level, not per-feature, given `Monti-Trentini-shop`'s schema doc already anticipates this
   exact fork for an unrelated feature.
4. **MT email-sending gap acknowledged as a related but separate blocker.** The brief is right
   to flag the overlap: any tracking that depends on **email** opens/clicks (vs. a link opened
   directly) inherits MT's existing email-sending problem (Salesforce → HubSpot Starter can't
   send custom HTML email; Make + Gmail API is the identified workaround, not yet built). Link-
   level tracking (the recipient clicking through to a hosted proposal) does **not** depend on
   this gap; email open-pixel tracking specifically would.
5. **Where the feature lives — platform vs. proposal-specific** (brief §5, new question 3,
   carried into open questions below) — changes ownership of the datastore/endpoint and whether
   it's built once (UDCS/platform capability) or per-tool (Proposal-Builder-only).
6. **Dashboard home** — if the should-have dashboard row ships, it needs the platform's Phase 2
   React shell (not started per `HANDOFF.md`) or a standalone minimal view built just for this
   feature. Either choice has cost implications noted in §4.

## 6. Risk notes

- **Architecture risk (highest):** picking Option A (pixel-on-static-file) to move fast, then
  discovering the must-have "unique link per recipient" row forces most of Option B's
  requirements anyway — a rework risk flagged explicitly in §3.1.
- **Scope-creep risk:** "engagement dashboard" is the row most likely to quietly balloon,
  because it's coupled to the platform's own unbuilt Phase 2 dashboard rather than being
  self-contained to this feature.
- **Dependency risk:** two features (Proposal Builder core, MT email-sending) that predate this
  request and are each independently unresolved are both load-bearing for parts of this work.
  Building tracking doesn't unblock either.
- **Data/privacy note (per brief's ask):** recipients are trade buyers (B2B), not consumers —
  materially lower regulatory exposure than a consumer-analytics product. But Monti Trentini is
  an Italian import business with EU-based trade contacts plausible among recipients, so an
  engagement-tracking feature (IP-adjacent data, timestamps, behavioral logging tied to an
  identifiable business contact) can cross into GDPR-relevant processing if any EU recipients
  are in scope. Recommend: no special-category data, keep retention short and documented, and
  a one-line disclosure in proposal footers is enough for v1 — but this should get an actual
  privacy-counsel read before a v1 launch, not just an engineering assumption.
- **Vendor risk:** avoid a third datastore vendor (Fauna) when the org's own prior work already
  points at Blobs/Supabase for the same underlying "outgrew JSON-in-git" problem (§3.2).
